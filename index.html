I like problems where the data looks fine until you look closely.

Case files.

01

Binary Log Data Pipeline

Riddell / Simbex · turning unreadable device logs into queryable tables
+

The challenge

Field devices stored their activity as binary-encoded logs in a production database, in more than one encoding format. Nobody could query them directly.

The approach

A Python (SQLAlchemy) pipeline that extracts the logs, decodes each format, and writes structured, analysis-ready records. I tested on small samples before running multi-week loads.

Technical details

Batched queries, retries with backoff and connection health checks keep long extracts running on a live database with unreliable connections.

NXT Log Analysis Tool

Riddell / Simbex · finding the unusual teams in fleet telemetry
+

The challenge

Engineering needed to see how each team's devices behaved across the fleet, and which ones looked unusual.

The approach

A command-line tool that parses JSON telemetry, groups events by type and team, and computes alert-to-event ratios. Date options (--days, --since) allow sample-first runs.

Technical details

When results showed 0% and 100% match rates, I traced them to a logic bug and fixed the matching rules before sharing anything.

Production API Monitoring Dashboard

Riddell / Simbex · one view of API health across the device fleet
+

The challenge

Handheld devices were hitting recurring authentication failures, and the team had no single view of API health.

The approach

A three-tier Datadog dashboard (system-wide, per-endpoint, per-team) for call volume, latency and error rates, filtered to the device traffic that mattered.

Technical details

Used Log Explorer and Watchdog to correlate logs across several days, and isolated the failure pattern to a specific client type and endpoint.

04

Fleet Health Dashboard

Riddell / Simbex · three data sources, one health score per base station
+

The challenge

Checking whether a base station was working meant looking in three places: the cellular SIM portal, Datadog logs and the device database.

The approach

A Streamlit app that pulls SIM status from the Soracom API, recent activity from Datadog, and logins, firmware, check-ins and latency from PostgreSQL, then joins them per station.

Technical details

Each station is scored Healthy, Partial or Offline, with 7-day Plotly trends, filters, a 15-minute cache and status changes tracked between runs.

04 // principles

How I think about data.

01 · validation

A perfect number is a suspicious number.

When my analysis showed a 100% match rate, it turned out to be a bug. Now I check results that look too good as hard as ones that look wrong.

02 · testing

Run it small before you run it big.

I build date windows into my tools so I can check a day of data before I trust a month of it.

03 · reliability

Plan for the connection to drop.

Production databases go away mid-query. Batching, retries and health checks are part of the pipeline, not extras.

04 · honesty

Say what the data can't tell you.

When a field is unreliable or a result is partial, I say so in the update rather than present it as final.
